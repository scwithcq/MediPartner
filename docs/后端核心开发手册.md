## 1. 项目定位与后端目标

MediPartner 是一个「基于大模型的信任型陪诊服务平台」，后端职责是承载 **C 端小程序（求助者 + 陪诊师）** 与 **B 端管理后台** 的全部业务能力。

后端必须在工程上落实三大核心价值：

1. **信任**：严谨的资金账户体系（余额 / 冻结 / 流水 / 乐观锁 / 幂等），100% 可追溯。
2. **AI 辅助决策**：RAG 知识库检索 + 大模型生成，支持通义千问 / 智谱 AI 可切换。
3. **可演进**：模块化单体，按业务领域清晰分界，为将来拆分微服务留好限界上下文。

### 3.2 单个模块内部分层（贫血模型 + DDD 分层）

每个 `module/xxx` 内统一四层，**模块间只允许通过 `xxxService`（接口）调用，禁止跨模块直接注入别的模块的 Mapper**：

```
module/order
├── controller/      # 表现层：仅做参数校验、鉴权注解、调 Service、组装 R<T>
├── service/         # 应用层：业务编排、事务边界、状态机驱动
│   └── impl/
├── domain/          # 领域对象：entity（DO）、dto（入参/出参）、enums、状态机定义
├── mapper/          # MyBatis-Plus Mapper
└── event/           # 领域事件（可选，用于解耦审计等）
```

**依赖方向**：`controller → service(接口) → mapper/domain`；跨模块仅依赖对方 `service` 接口（依赖倒置）。`common` 与 `infra` 对所有人可见，任何 `module` 不得反向依赖 `admin`（admin 是聚合层）。

## 4. 全局统一规范（重中之重）

> 这一节是"参数不能乱设置"的落点。**所有接口、所有模块必须遵守**，否则前后端联调和跨模块调用会乱。

### 4.1 统一响应体 `R<T>`

所有 Controller 方法（含异常）一律返回如下结构，**禁止裸返回实体 / Map / 字符串**：

```json
{
  "code": 0,
  "message": "success",
  "data": { },
  "traceId": "c3f1...",
  "timestamp": 1730000000000
}
```

```java
public class R<T> {
    private int code;        // 0 成功；非 0 见错误码
    private String message;  // 提示信息
    private T data;          // 业务数据
    private String traceId;  // 链路追踪 id，异常排查用
    private long timestamp;  // 毫秒时间戳
}
```

- 成功：`R.ok(data)` → `code=0`。
- 失败：抛 `BizException(ErrorCode)`，由全局异常处理器统一转成 `R<T>`，**Controller 内不写 try/catch**。
- `traceId` 由 MDC 过滤器自动填充（贯穿日志与响应）。

### 4.2 分页响应体 `PageResult<T>`

所有列表/分页接口统一返回：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "records": [ ... ],
    "total": 37,
    "pageNum": 1,
    "pageSize": 10
  },
  "traceId": "...",
  "timestamp": 1730000000000
}
```

- 分页入参统一为请求 DTO 继承 `PageQuery { pageNum=1, pageSize=10 }`。
- `pageSize` 上限 **100**，超出由校验器兜底为 100。
- 排序字段用白名单校验（`sortBy` + `order=asc|desc`），**不允许直接把排序字段拼进 SQL**。

### 4.3 统一错误码 `ErrorCode`

错误码分段规划，**新增错误码必须先登记，不得随意取数**：

| 码段 | 含义 | 示例 |
| :--- | :--- | :--- |
| `0` | 成功 | — |
| `1xxx` | 通用/参数/认证 | 1001 参数校验失败；1002 未登录；1003 无权限；1004 Token 过期 |
| `2xxx` | 用户域 | 2001 用户不存在；2002 手机号已绑定；2003 入驻审核未通过 |
| `3xxx` | 订单域 | 3001 订单不存在；3002 订单状态不允许该操作；3003 手慢一步已被抢走；3004 接单已达上限；3005 不在接单距离范围 |
| `4xxx` | 钱包域 | 4001 余额不足；4002 幂等键重复；4003 提现金额非法；4004 账户不存在 |
| `5xxx` | 工单/评价域 | 5001 工单不存在；5002 已申诉过；5003 不可评价 |
| `6xxx` | AI/知识库域 | 6001 知识库未发布；6002 大模型调用失败；6003 文档解析失败 |
| `9xxx` | 系统/外部依赖 | 9001 系统异常；9002 外部服务超时 |

`ErrorCode` 用枚举实现：`code + message` 常量，`BizException` 携带该枚举。

### 4.4 全局字段命名与类型约定

| 约定项 | 规则 |
| :--- | :--- |
| 数据库字段 | 蛇形 `snake_case`（`user_id`、`txn_no`、`created_at`） |
| Java 字段 / JSON 字段 | 驼形 `camelCase`（`userId`、`txnNo`、`createdAt`），由 MyBatis-Plus `map-underscore-to-camel-case=true` + Jackson 自动映射 |
| 主键 ID | 全部 **雪花算法 Long**（MyBatis-Plus `ASSIGN_ID`），JSON 传 `number`，前端 JS 侧注意 Long 精度（见 4.6） |
| 业务编号 | 字符串，如订单号 `orderNo`、流水号 `txnNo`、工单号 `appealNo`，格式统一 `前缀+yyyyMMddHHmmss+6位随机`，例如 `MP20241201103000123456` |
| 金额 | 数据库 `DECIMAL(12,2)`、Java `BigDecimal`、**JSON 用字符串 String**（如 `"100.00"`），单位"虚拟币"，杜绝浮点精度问题 |
| 时间 | 数据库 `DATETIME`、Java `LocalDateTime`、JSON 字符串 `yyyy-MM-dd HH:mm:ss` |
| 状态/枚举 | 数据库存 `INT` 或 `VARCHAR` 码值，Java 用枚举，**JSON 传码值**（见 7.2 状态码表），不用中文 |
| 布尔 | `TINYINT(1)` ↔ `Boolean` ↔ JSON `true/false` |
| 手机号/OpenID | 一律脱敏后返回（`138****1234`），OpenID 永不直接返回前端，仅以 token 身份承载 |

### 4.5 鉴权与路由规范

- 路由前缀：`/api/auth/**`（认证）、`/api/user/**`（普通用户）、`/api/worker/**`（陪诊师）、`/api/admin/**`（管理员）、`/api/common/**`（公共只读/文件）。
- 认证方式：`Authorization: Bearer <JWT>`；JWT 有效期 **2 小时**，支持 `refreshToken` 刷新。
- 角色模型：`USER`（普通用户）、`WORKER`（陪诊师）、`ADMIN`（管理员）。一个用户可同时是 `USER + WORKER`（审核通过后追加角色）。
- 角色注解：`@PreAuthorize("hasRole('WORKER')")` 等；`/api/admin/**` 仅 `ADMIN`。

### 4.6 Long 精度与幂等

- **Long 精度**：主键雪花 ID 超过 JS 安全整数，前后端约定——若前端 JS 无法原生处理，ID 在 JSON 中序列化为 **String**（全局 Jackson `ToStringSerializer` 针对 Long id 字段）。此项在阶段 1 就定死，避免后期到处改。
- **幂等**：写操作接口（下单、抢单、充值、确认完成、提现）请求头带 `Idempotency-Key`（或业务号做幂等键）；资金类操作以 `txnNo` 唯一索引兜底，重复请求返回同一结果而非重复扣款。

## 6. 领域模块划分与内部依赖契约

### 6.1 模块职责边界

| 模块 | 职责 | 对外暴露的 Service 接口（供其他模块调用） |
| :--- | :--- | :--- |
| `user` | 用户、角色、陪诊师审核、信用分 | `UserService.getById`、`WorkerService.getProfile`、`CreditService.getScore/addRecord` |
| `order` | 需求工单、订单、状态机、抢单、接单上限 | `OrderService.getByNo`、`OrderService.countActive(workerId)`、`OrderService.isState(orderId, ...)` |
| `wallet` | 账户、流水、提现 | `WalletService.freeze(...)`、`WalletService.unfreeze(...)`、`WalletService.settle(...)`、`WalletService.refund(...)` |
| `ticket` | 申诉工单、仲裁 | `AppealService.create(orderId, ...)`、`AppealService.arbitrate(...)` |
| `review` | 评价、追评、回复 | `ReviewService.create(...)`、`ReviewService.reply(...)`、`ReviewService.calcGoodRate(workerId)` |
| `knowledge` | 文档、切片、向量化、检索 | `KnowledgeService.search(query, topK)`、`KnowledgeService.getActiveSlices()` |
| `ai` | 发单助手、陪诊报告、Provider 策略 | `AiService.recommendDepartment(...)`、`AiService.generateReport(orderId)` |
| `admin` | 审核、干预、仲裁编排、审计 | `AuditLogService.record(...)`（供所有人工干预操作调用） |

### 6.2 事务边界约定（关键）

- **确认完成结算**是"强一致性事务"，必须在 `order` 模块的应用服务内用 `@Transactional` 包裹：
  `解冻扣款 + 陪诊师入账 + 写两条流水 + 更新订单状态`，四步同一事务，任一失败整体回滚。
- **抢单**是乐观锁短事务：`UPDATE service_order SET worker_id=?, order_status=20, version=version+1 WHERE id=? AND version=? AND order_status=10`，影响行数 0 即失败。
- AI 报告生成、PDF 解析走 **异步**（RabbitMQ），不得阻塞用户确认/上传接口。

## 7. 订单状态机（Spring StateMachine）

### 7.1 状态与事件枚举定义

```java
public enum OrderState {
    WAITING_ACCEPT(10),  // 待接单（资金已冻结）
    ACCEPTED(20),        // 已接单/待服务
    IN_SERVICE(30),      // 服务中
    PENDING_CONFIRM(40), // 待确认
    COMPLETED(50),       // 已完成
    CANCELLED(60),       // 已取消
    ABNORMAL(70);        // 异常
}

public enum OrderEvent {
    CREATE,        // 用户下单
    ACCEPT,        // 陪诊师抢单
    START,         // 开始服务
    FINISH,        // 结束服务（需上传凭证）
    USER_CONFIRM,  // 用户确认完成
    AUTO_CONFIRM,  // 超时自动确认
    TIMEOUT_CANCEL,// 无人接单超时取消
    USER_CANCEL,   // 用户取消（仅待接单）
    MARK_ABNORMAL, // 服务超时异常标记
    ADMIN_CANCEL,  // 管理员取消
    ADMIN_REFUND;  // 管理员强制退款
}
```

### 7.2 状态流转表（转移规则，唯一权威）

| 当前状态 | 触发事件 | 目标状态 | 前置条件 | 附加动作 |
| :--- | :--- | :--- | :--- | :--- |
| — | `CREATE` | `WAITING_ACCEPT` | 用户已冻结资金 | 写流水(冻结) |
| `WAITING_ACCEPT` | `ACCEPT` | `ACCEPTED` | 乐观锁抢占成功、未达接单上限、信用分≥60 | 记录接单时间 |
| `WAITING_ACCEPT` | `USER_CANCEL` | `CANCELLED` | 仅下单人 | 解冻退款 |
| `WAITING_ACCEPT` | `TIMEOUT_CANCEL` | `CANCELLED` | 24h 无人接单 | 解冻退款 |
| `ACCEPTED` | `START` | `IN_SERVICE` | 陪诊师本人 | 记录 GPS + 时间戳 |
| `IN_SERVICE` | `FINISH` | `PENDING_CONFIRM` | 已上传就诊凭证 | 触发 AI 报告异步生成 |
| `PENDING_CONFIRM` | `USER_CONFIRM` | `COMPLETED` | 用户本人 | **结算事务**（解冻扣款+入账） |
| `PENDING_CONFIRM` | `AUTO_CONFIRM` | `COMPLETED` | 48h 未确认 | 结算事务 |
| `IN_SERVICE` | `MARK_ABNORMAL` | `ABNORMAL` | 服务超过 12h 未结束 | 后台高亮预警 |
| `ABNORMAL` | `ADMIN_CANCEL`/`ADMIN_REFUND` | `CANCELLED` | 管理员 | 写审计 + 退款 |
| 任意非终态 | `ADMIN_CANCEL` | `CANCELLED` | 管理员 | 写审计 + 退款 |

**终态**：`COMPLETED`、`CANCELLED`。终态不可再流转（状态机返回错误/告警）。

### 7.3 状态机落地约定

- 每个订单的流转都通过 Spring StateMachine 发起 `sendEvent(event)`，**禁止直接 `setOrderStatus(...)`**。
- 状态机状态持久化：以 `service_order.order_status` 为唯一事实来源（Redis 只做缓存加速，不做状态权威）。
- 每个成功/失败流转，记录结构化日志：`orderNo + 前状态 + 事件 + 后状态 + 操作人 + 时间`。

## 9. 跨模块相互照应关系（接口联动清单）

> 这些是"相互照应"的接口，阶段开发时**必须成对打通**，字段与事务边界严格按下表。

| 场景 | 触发接口 | 联动模块/接口 | 一致性要求 |
| :--- | :--- | :--- | :--- |
| 下单 | `POST /api/order` | `wallet.freeze(userId, orderNo, amount)` | 冻结失败则下单失败；冻结成功但下单失败需回滚解冻 |
| 抢单 | `POST /api/worker/order/{no}/accept` | `order.countActive(workerId)` + `credit.getScore(workerId)` | 校验 + 乐观锁同事务 |
| 取消/超时取消 | `order` 状态机 `TIMEOUT_CANCEL/USER_CANCEL` | `wallet.unfreeze(...)` | 解冻写流水，幂等 |
| 确认完成 | `POST /api/order/{no}/confirm` | `wallet.settle(...)`（解冻扣款+入账+两条流水） | **强一致事务**，见 6.2 |
| 评价 | `POST /api/order/{no}/review` | `review.create(...)` + `review.calcGoodRate(workerId)` | 完成后更新陪诊师好评率 |
| 申诉 | `POST /api/order/{no}/appeal` | `ticket.create(...)` 关联订单 | 同一订单不可重复申诉（`5002`） |
| 仲裁退款 | `POST /api/admin/appeal/{no}/arbitrate` | `wallet.refund(...)` + `audit.record(...)` | 退款走流水 + 审计 |
| 审核通过 | `POST /api/admin/worker/apply/{id}/audit` | `user.addRole(USER_ID, WORKER)` + `worker.initCredit(100)` | 通过后即时获得接单角色 |
| AI 发单 | `POST /api/ai/assist` | `knowledge.search(query, 3)` → 拼 Prompt → 大模型 | 仅检索 `status=已生效` 切片 |
| AI 报告 | `order` 状态机 `FINISH` | `ai.generateReport(orderId)`（RabbitMQ 异步） | 异步生成，不阻塞 FINISH |

**内部资金接口签名（唯一）**，`wallet` 模块实现并导出：

```java
public interface WalletService {
    String freeze(Long userId, String orderNo, BigDecimal amount);   // 返回 txnNo
    void unfreeze(String orderNo);                                   // 解冻
    void settle(String orderNo);                                     // 解冻+扣款+入账
    void refund(String orderNo, BigDecimal amount);                  // 退款（仲裁/管理员）
}
```

### 11.2 第一阶段验收清单（Definition of Done）

- [ ] 三张核心表（`sys_user`、`service_order`、`wallet_account`、`wallet_transaction`）由 Flyway 自动建出。

- 功能分支：`feature/阶段N-模块名`，如 `feature/phase1-order`；修复 `fix/xxx`。

### 12.2 Commit Message 规范（Conventional Commits）

```
<type>(<scope>): <subject>

type: feat | fix | docs | refactor | test | chore | build
scope: user | order | wallet | ticket | review | ai | knowledge | admin | common | infra
subject: 简明扼要，中文或英文均可，但全程统一
```

示例：`feat(order): 实现抢单乐观锁与接单上限校验`、`feat(wallet): 增加结算事务与流水幂等键`。

### 12.3 `.gitignore` 必须忽略（敏感信息绝不入库）

```
application-local.yml        # 本地密钥配置
*.log
target/
.idea/                       # 已有
*.iml
```

- 密钥（微信 AppSecret、通义/智谱 API Key、数据库密码）只放在 `application-local.yml`（已忽略），仓库里提交 `application-example.yml` 模板。
- Docker Compose 里的密码建议用 `.env`（加入 `.gitignore`），提供 `.env.example`。

### 12.4 提交节奏
- 每完成一个可验收的原子功能（对应 11.1 任务粒度）提交一次，不积压大提交。
- 每次提交前确保 `mvn test` 通过。

## 13. 风险点与注意事项

1. **Spring AI 1.0 与 Boot 3.5 的版本兼容**：以官方 BOM 为准锁定版本；DashScope 与智谱的 starter 依赖坐标在落地时核对（可先只接一家跑通，另一家按策略接口留位）。
2. **Spring StateMachine 状态持久化**：不引入额外持久化状态库，以 `service_order.order_status` 为唯一事实来源；状态机只做"流转合法性校验 + 触发动作"，避免状态机内部状态与 DB 漂移。
3. **乐观锁版本冲突重试**：抢单/结算遇到版本冲突时重试 1~2 次，超出转失败（记录日志），避免无限循环。
4. **资金不得走 Redis**：Redis 仅缓存/限流，余额扣减必须数据库事务（设计文档 6.2 明确）。
5. **幂等键兜底**：`wallet_transaction.txn_no` 唯一索引是资金安全的最后防线，重复请求以幂等键拦截。
6. **敏感信息**：身份证号加密存储、手机号脱敏返回、OpenID 不外泄。
7. **AI 回答可控**：RAG 强制"基于检索片段回答"，并附引用来源；prompt 内显式约束"资料未覆盖时明确说明，不臆造医疗建议"。
